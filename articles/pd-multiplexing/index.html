PD-Multiplexing：不搬 KV 的另一条路

用 GPU 内空间复用隔离 Prefill 与 Decode，在共享 KV pool 的同时动态分配 SM。

ORIGINAL · PD-Multiplexing: Unlocking High-Goodput LLM Serving with GreenContext

single instance · shared KV pool · GreenContext SM partition · SLO-aware dispatcher

CORE THESIS

P/D 的本质是隔离两种执行节奏，不一定要求物理分离；如果 GPU 能提供细粒度空间隔离，就可能保留共享状态并避免 KV migration。

它提供了经典 P/D disaggregation 的重要反例，迫使读者区分“资源隔离”“独立扩缩容”和“状态搬运”三件常被捆绑的事。

01
ARGUMENT 01

为什么重新考虑物理分离

跨实例 PD 需要搬运 KV，并可能因固定 P:D 划分产生资源碎片。

在同一实例内共享 KV pool，可消除 handoff 数据面。

阅读注解

共享状态减少了搬运，但也重新引入同机故障域和容量耦合；它解决的是一组代价，同时放弃另一组自由度。

先拆解 PD 的各项收益，不要把它们视为不可分割套餐。

02
ARGUMENT 02

GreenContext 的空间复用

为不同 CUDA streams 分配独立 SM 集合，让 Prefill 与 Decode kernels 并发执行。

SM 配比可随 workload 和 SLO 调整，使空闲资源在 P/D 间流动。

阅读注解

空间分区要面对 kernel scaling 非线性：某些 kernel 在少量 SM 下效率骤降，静态百分比分配不能代表真实吞吐。

需要 profile 每类 kernel 的 SM sensitivity curve。

03
ARGUMENT 03

Bubble-less Engine 与 SLO Dispatcher

单线程调度器协调异步 P/D streams，避免 Python 控制路径本身产生竞争。

dispatcher 根据 profiling 生成满足 ITL 约束的 multiplex plan。

阅读注解

这里把系统问题转化为资源分配控制问题：核心输入是 workload 预测和 kernel profile，输出是可执行的 SM/调度计划。

SLO-aware scheduling 需要在线反馈来抵抗分布漂移。

01机制

PD-Multiplexing 保留了 PD 的哪些收益，又放弃了哪些收益？

查看提示

区分执行隔离、状态共享、硬件隔离与独立扩缩容。

参考推导

它保留 P/D kernel 并发与一定的执行隔离，同时共享 KV、避免迁移并动态借用 SM；但 P/D 仍在同一 GPU/实例和故障域，不能像物理分离那样独立选硬件、扩大节点或完全独立扩缩容。

02推导

为什么固定 50/50 SM 分区通常不是好策略？

查看提示

流量比例和 kernel 对 SM 的扩展曲线都在变化。

参考推导

P/D 到达率、input/output 长度与 batch 会动态变化，且不同 kernels 对 SM 数的吞吐不是线性关系。固定分区可能让一侧空闲、另一侧违约，或把 kernel 放在低效率区间。

03设计

什么时候选择 Multiplexing、Colocated 或物理 PD？

查看提示

构造三个 workload 区间。

参考推导

低负载/短 prompt 选简单 colocated；单机且有明显干扰、KV 搬运昂贵、流量比例变化快时考虑 multiplexing；规模大、阶段比例长期失衡、需要不同硬件/并行度或严格故障隔离时选物理 PD。最终以 SLO goodput 验证。
