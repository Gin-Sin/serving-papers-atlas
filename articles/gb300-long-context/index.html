CORE THESIS

长上下文 serving 的 P 侧受 TTFT 与 Attention compute 约束，D 侧受 KV capacity 与带宽约束，因此必须使用不同扩展方向。

这是阶段异构设计的优秀端到端案例，文章同时给出 P/D 控制面、TTFT、batch capacity、TPS/GPU 与 TPS/user 的取舍。

01
ARGUMENT 01

Prefill：用 PP 扩展长序列计算

128K prompt 让 Prefill Attention 和 TTFT 成为第一瓶颈。

Chunked PP 与动态 chunking 将长 prompt 流水化，并配合更快 Attention kernel。

阅读注解

此时 Prefill 的目标不只是最大吞吐，还要控制单请求 fill/drain 与首 token 时间。

P 侧应同时报告 input TPS 与 TTFT。

02
ARGUMENT 02

Decode：更大 HBM 转化为 Batch

长上下文让每个请求的 KV footprint 增大，Decode 容量首先受可驻留请求数限制。

Wide-EP 与更多 HBM 提高有效 batch，并摊薄 MoE GEMM 与权重读取。

阅读注解

HBM 容量收益只有在调度器能稳定维持大 batch、且 A2A 未成为瓶颈时才会变成 TPS。

容量、batch 和通信必须形成闭环解释。

03
ARGUMENT 03

MTP 与控制面的角色

MTP 减少目标模型迭代次数，可提升 per-user decode speed，但收益依赖接受率和 batch。

Dynamo 协调 P/D workers、KV-aware routing、生命周期和前后处理。

阅读注解

当数据面被拆散后，控制面不再是外围组件：它决定 KV 去哪、worker 何时可用，以及失败后状态如何回收。

PD benchmark 应把路由与状态管理开销包含在端到端指标内。

01机制

为什么长上下文 Decode 更容易成为 KV-capacity-bound？

查看提示

每个活跃请求的历史状态随 ISL 如何变化？

参考推导

Decode 必须为每个活跃请求保留完整历史 Attention 状态。ISL 增长会线性抬高单请求 KV footprint，降低可并发 batch；即使每步计算相近，容量和 KV 访问都会恶化。

02推导

增加 HBM 后 TPS 为什么不一定按容量同比增长？

查看提示

更大 batch 会触发哪些新的瓶颈？

参考推导

更大 batch 可能让 MoE A2A、Attention bandwidth、调度开销或专家 skew 成为新瓶颈；同时延迟 SLO 可能不允许把 batch 填到容量上限。

03设计

如何为 128K/8K 和 8K/128K 两类 workload 规划不同 P:D 比例？

查看提示

比较输入计算和输出驻留时间。

参考推导

128K/8K 需要更高 Prefill capacity 与 PP 扩展；8K/128K 则让请求长时间占用 Decode KV 和执行步数，需要更多 Decode capacity。两者都应在目标 TTFT/TPOT 下按真实到达率求 Pareto 配比。
