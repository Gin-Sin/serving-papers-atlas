HiCache：把 Radix Tree 扩展成分层 KV 页表

让 GPU、CPU 与远端存储组成一个可调度的 KV hierarchy，并为不同层分别优化布局、搬运与写回策略。

CORE THESIS

分层 KV Cache 的关键不是简单增加容量，而是让命名、放置、I/O 布局和请求调度共同决定一次命中是否比重算更便宜。

文章从 GPU-only RadixAttention 的容量上限出发，完整讨论了 CPU/存储层的数据面和控制面，是理解外部 KV 系统的最佳过渡材料。

ARGUMENT 01

GPU-only Prefix Cache 的容量悬崖

长上下文和多轮会话会迅速占满 GPU KV pool，历史前缀被淘汰后仍需重复 Prefill。

HiRadixTree 作为页表记录 KV 当前位于 GPU、CPU 或外部存储，由 cache controller 管理层级间加载与备份。

阅读注解

扩大缓存层级改变了“free block”的语义：GPU eviction 不再等于数据失效，而可能只是 residency 变化。调度器需要区分 miss、remote hit 和 in-flight。

缓存命中必须带上 location 与 readiness 才对调度有意义。

02
ARGUMENT 02

计算布局与 I/O 布局为什么分离

GPU KV pool 保持 layer-first，以兼容 attention kernels 的逐层访问。

CPU 与存储层使用 page-first，把同一 page 的多层数据连续放置，从而形成更大的传输事务，并配合 zero-copy 和 GPU-assisted I/O。

阅读注解

最佳计算布局未必是最佳传输布局。分层系统常需要在边界完成 layout-aware gather/scatter；如果转换成本未被统计，理论带宽收益会失真。

数据布局是 kernel contract，也是 I/O contract。

03
ARGUMENT 03

如何把搬运隐藏在计算后面

CPU hit 可按 layer 流水加载：第 N 层计算时预取后续层 KV，让传输与 forward 重叠。

外部存储延迟更高且波动更大，可选择 best-effort、超时取消或等待完成等 prefetch 行为。

阅读注解

是否等待远端 cache hit 本质上是“剩余搬运时间 vs 重算时间 vs queueing 影响”的在线决策，静态 hit/miss 策略很难在所有负载下最优。

优化目标是 exposed load latency，而不是后台 I/O 吞吐。

04
ARGUMENT 04

写策略与可插拔后端

write-through、selective write-through 与 write-back 在复用率、带宽和数据持久时间之间取舍。

存储后端只需实现 get、exist、set，调度与同步由中心 controller 统一处理，已能连接 Mooncake、3FS、NIXL 等路径。

阅读注解

简洁接口提升可替换性，但并不会消除语义差异：一致性、失败恢复、对象粒度、带宽和尾延迟仍要由上层策略显式吸收。

控制面接口越统一，性能与一致性契约越要写清楚。

01机制

为什么 GPU 使用 layer-first，而 CPU/存储偏向 page-first？

查看提示

分别沿 attention 计算和一次远端读取的访问方向观察。

参考推导

attention 按层执行，需要快速访问该层所有活跃 pages，因此 GPU 保持 layer-first；外部命中通常要恢复一个 token page 在所有层的 KV，page-first 可把数据组成更大的连续 I/O，减少小事务和描述符开销。

02推导

远端命中已经确认时，为什么仍可能选择取消 prefetch 并重算？

查看提示

命中不等于及时可用。

参考推导

如果远端尾延迟、排队或剩余数据量使完成时间超过本地重算，而且等待会阻塞当前 batch 的 TTFT，那么 remote hit 的经济价值为负。调度器应比较预计完成时间和重算成本，而不是无条件等待命中。

03设计

如何评估 write-through、selective 与 write-back 三种策略？

查看提示

构造不同复用率和带宽压力的 workload。

参考推导

按 prefix 复用间隔、会话长度、后端带宽和容量分桶，记录写流量、读命中、淘汰前复用次数、TTFT 与重算 FLOPs；write-through 适合高复用且写带宽充足，selective 适合热点明显，write-back 适合慢层容量或带宽紧张但需承担 eviction/故障前未落盘风险。
