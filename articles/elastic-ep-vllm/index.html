Elastic EP：运行中改变并行拓扑

不停服增减 DP workers、重建 EP group、迁移专家，并与 EPLB 和 NIXL EP 协调。

ORIGINAL · Elastic Expert Parallelism in vLLM

DP workers resize · shared EP group changes · online expert redistribution

CORE THESIS

当 EP group 同时是性能域和故障域时，生产系统必须把拓扑本身从静态启动参数升级为可事务化变更的运行时状态。

文章详细给出 scale-up/down 的阶段、standby groups、权重传输、切换点与 EPLB reshuffle，是研究分布式 serving reconfiguration 的一手材料。

ARGUMENT 01

哪些状态必须一起改变

增减 DP workers 会改变 EP group size、rank membership、expert placement 和 scheduler 可见容量。

通信组、模型权重与请求路由若不同步切换，会出现 deadlock 或错误 expert ownership。

阅读注解

Elasticity 不是“多启动一个进程”，而是跨控制面、执行面与通信面的分布式 schema migration。

先列出所有依赖 world size 的状态。

02
ARGUMENT 02

Standby Group 与切换点

新 workers 先初始化并加入备用通信结构，完成专家映射与权重传输。

所有 ranks 在受控边界完成 switch，再触发 EPLB 根据新拓扑重排。

阅读注解

真正困难的是定义线性化点：切换前后的请求必须分别只看到一种完整拓扑，不能处于半更新状态。

在线重配置需要版本化 topology epoch。

03
ARGUMENT 03

从弹性走向容错

相同重配置路径可用于移除失败 rank、恢复容量并重新分布专家。

NIXL EP 的通信模型有助于减少重新初始化，并提供失败检测能力。

阅读注解

弹性与容错共享机制，但触发条件不同：计划扩缩容可以等待安全点，非计划故障需要处理不完整 collective 与未知状态。

不要把可缩容直接等同于已容错。

01机制

为什么 resize DP 会改变 EP group？

查看提示

vLLM 中 experts 跨哪些 workers 共享？

参考推导

DP Attention workers 各自处理请求，但其 MoE layers 共同组成 EP group；增加或移除 DP worker 就会改变参与专家分片与 token dispatch 的 ranks，因此 expert placement 和通信域都要更新。

02推导

为什么必须在 switch 后再次执行 EPLB reshuffle？

查看提示

旧映射针对旧 ranks 和旧容量。

参考推导

world size 与设备集合改变后，旧 logical-to-physical expert mapping 可能不均衡或指向已删除 ranks；即使基本权重已分发，也要按新拓扑和近期负载重新优化冗余与放置。

03设计

怎样定义一次安全的 scale-down 事务？

查看提示

考虑停止新流量、排空、权重保障、切换和回滚。

参考推导

标记 topology epoch，停止向待移除 ranks 分配新请求；排空或迁移其请求，确保 surviving ranks 已持有所需专家；建立新通信组并 barrier，在统一 linearization point 切换路由/映射，验证健康后释放旧组，失败则回滚 epoch。
