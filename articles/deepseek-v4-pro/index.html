DeepSeek-V4-Pro：一个模型，多套 Serving Profile

在 H20 约束下分别优化长 Prefill、低延迟 Decode 与高吞吐 Decode，而不是寻找万能配置。

CORE THESIS

模型部署的产物不应是一条启动命令，而应是覆盖不同 workload 与 SLO 区间的一组可解释 profiles。

文章罕见地把“为什么不用 EP”“为什么低延迟用 PP2-TP8”“为什么高吞吐用 DP32-EP32”放在同一套硬件限制中比较。

建议先打开官方原文

本站按原文论证顺序提供中文导读与注解，不重新托管全文。

阅读官方原文
01
ARGUMENT 01

从硬件约束定义 Profiles

H20 缺少 Blackwell 的原生 FP4 与更大 HBM，权重 footprint、KV capacity 和通信更紧张。

短输入、百万上下文、batch-1 与高并发需要不同目标函数。

阅读注解

“同模型同卡型”仍不足以决定配置；workload distribution 和 SLO tier 才是 profile 的索引。

配置系统应按 workload envelope 组织，而非按模型名组织。

02
ARGUMENT 02

Prefill 为什么选择 MoE-TP

大 Prefill batch 下 token 分布可能让 EP rank 出现专家 skew 与同步长尾。

MoE-TP 让每个 rank 对相同 routed tokens 执行切分计算，牺牲一些通信换取可预测平衡。

阅读注解

EP 不是 MoE 的唯一正确答案。Prefill token 多、计算密集且对负载不均敏感时，TP 的规则性可能更有价值。

并行策略应依据实际 routing shape，而不是模型标签。

03
ARGUMENT 03

两种 Decode Frontier

低延迟路径用 PP2-TP8 与 DSpark，围绕 batch 1 和 TPOT 优化关键链。

高吞吐路径用 DP/EP、量化、更多 KV capacity 与 overlap，面向大并发。

阅读注解

这两条曲线优化的是不同目标，不应被压成一个“最佳 TPS”排名。正确产物是带 SLO 条件的 Pareto frontier。

Latency frontier 与 throughput frontier 必须分别测量和运营。

COMPREHENSION CHECK

把结论重新推导一遍

先独立作答，再展开提示或参考思路。设计题没有唯一答案，重点是能否明确约束、关键路径与验证方法。

01机制

为什么 MoE-TP 在 Prefill 可能比 MoE-EP 更稳定？

查看提示

考虑 expert skew 是否会变成 rank skew。

参考推导

EP 将不同 experts 放在不同 ranks，routing 偏斜会造成 rank 工作量差异并被 collective 放大；TP 让 ranks 对同一 routed token 集合做规则切分，工作更一致，代价是更频繁同步。

02推导

为何 batch-1 低延迟路径可能选择 PP2-TP8，而不是更大的 EP？

查看提示

小 batch 无法摊薄哪些成本？

参考推导

batch 1 下 expert GEMM 很小，Wide-EP 的 A2A 与同步成本难以摊薄；较小 TP 域配合 PP 可切下模型容量并保留更可预测的关键路径，再用 speculative decoding 减少 step 数。

03设计

如何把多 profile 部署接入在线 router？

查看提示

需要请求特征、实时容量和反馈闭环。

参考推导

按 ISL、预测 OSL、priority/SLO、prefix hit 与并发成本分类，再结合各 profile 的 queue、KV headroom 和健康度路由；设置 fallback 与 admission control，并根据完成请求的 TTFT/TPOT 反向校准分类边界。
